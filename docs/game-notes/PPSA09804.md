## Current Status

- Compatibility Status: Booting
- Last Milestone Reached: The title now boots cleanly through its **entire platform/OS layer with zero unresolved imports** and reaches deep Unity/IL2CPP runtime + audio-subsystem initialization (~91,000 HLE import calls, up from 2,736 — a ~33x increase). Reaching this point required: (a) the IL2CPP embedding API scaffolding (`il2cpp_api_lookup_symbol`/`register_symbols` + ~64 of ~220 il2cpp_* functions); (b) filling in every platform NID the game requests along the way — `sceKernelPollSema`, `scePthreadGetprio`/`Setprio`/`AttrGetinheritsched`/`RegisterThreadDeathHook`, `snprintf`, `sincos`, `sceKernelIsPs4Process`, the full `sceUserServiceGetAccessibility*` family, `sceNpGetAccountId`/`NpId`/`AccountCountry` (report SIGNED_OUT), the `sceMsgDialog*` lifecycle, `scePadCtrlpSyncInit`, `sceMouseMbusInit`, `sceAgcDriverSetFlip`/`SetResourceUserData`, the `sceAjm*` audio lifecycle, `sceAudioOutSetUsbVolume`; and (c) fixing a stack-canary corruption caused by the NP getters overwriting a caller's error-path stack scratch.
- Terminal state: a **deterministic access violation deep in Unity runtime code** (main thread computing a garbage array/string length, or an audio worker thread calling through a garbage function pointer — whichever fires first under thread timing). Both stem from the ~160 still-generic IL2CPP metadata functions returning 0/garbage where real class/method/field data is required. This is the IL2CPP-VM boundary, not a missing platform import.

Before the branch changes, the title failed at the raw entry address after

meaningful comparison; the short duration ends at a known crash and is not a
game-performance result.

### IL2CPP HLE scaffolding update (branch `feat/ppsa09804-il2cpp-hle`)

Adding host implementations for `il2cpp_api_lookup_symbol`/`il2cpp_api_register_symbols`
plus ~64 of the ~220 IL2CPP embedding API functions (see `src/SharpEmu.Libs/Il2Cpp/`)
lets boot progress roughly 7.6x further before faulting. The run is still
deterministic, but now takes noticeably longer wall-clock time (heavier
per-import work: real allocations, thread-local buffers, `System.Threading.Monitor`
locks) and needs a longer timeout to reach its terminal state instead of being
killed mid-flight.

| Metric | Run 1 | Run 2 | Run 3 | Aggregate |
|---|---:|---:|---:|---:|
| Duration | 32.887 s | 32.890 s | 32.784 s | 32.854 s average |
| Peak working set | 298.0 MiB | 258.1 MiB | 293.0 MiB | 298.0 MiB maximum |
| Highest import | 20,881 | 20,880 | 20,882 | ~20,880 (small variance from real background threads) |
| Terminal state | access_violation | access_violation | access_violation | Deterministic |
| First frame | No | No | No | No |

Reproduce with a longer timeout than the original 15s default:

```powershell
.\scripts\benchmark-game.ps1 -TitleId PPSA09804 -Runs 3 -TimeoutSeconds 60
```

The new terminal fault is a read access violation at offset `0xA0` from a
null pointer (`RIP=0x00000008013726B8`, `mov rbx, [r14+0xA0]`) - i.e. guest
code dereferencing a field on an object/class pointer that one of the ~160
still-unimplemented IL2CPP symbols (class metadata, reflection, object
construction) returned as 0. This is the expected next wall: implementing
those requires parsing `global-metadata.dat` and building a real class/method
registry, not just more leaf-function stubs.

### Full platform-import coverage update

A follow-up pass filled in **every** platform NID the game requests along its
boot path (see "Last Milestone Reached" for the list) plus the `sceAjm*` audio
lifecycle, and fixed a stack-canary corruption in the NP account getters. With
those in place the game boots with **zero unresolved imports** and runs ~33x
further than the original baseline. Two robustness guards were also added to
`DirectExecutionBackend`: guest threads created with a non-executable entry
point are now skipped (logged) instead of jumping into unmapped memory, and the
raw vectored-exception handler will unwind a guest execute-fault to a plausible
stack return when one exists, so a single garbage call abandons only that call
rather than the whole process.

## Observed Behavior

The executable loads and begins Unity initialization without opening a window.
It reads its boot data, configures libc state, reserves the expected virtual
memory pools, and queries mouse and user-service capabilities. Unity requests
hundreds of IL2CPP API addresses through `il2cpp_api_lookup_symbol`. Since
those addresses are unavailable, a stored error value is eventually executed
as code. The run is deterministic across all three benchmark samples.
